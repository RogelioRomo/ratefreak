# glibc iconv caller investigation

2026-11-25. Focused supported-flow assessment for supplied trigger conditions: CVE-2026-121757 CP949 to UTF-8//IGNORE, CVE-2026-121758 ISO-2022-CN-EXT decoding, and CVE-2026-124024 UCS-4 to IBM1390/IBM1399. No product changes or persistent-instance access. This does not independently establish advisory version applicability or overall security clearance.

## Established boundaries

The existing `../gconv-probes.json` proves all affected conversion pairs can be opened in the phase-2 API/web/tools images. No converter-absence disposition is valid. Existing binary probes also show real `iconv_open` imports in web's bundled libvips and every image's libstdc++. `existing-binary-probe-iconv.json` retains those results with their original image identities; they are phase-2 observations and must not be relabeled as a new-image exhaustive scan.

### Web image path

`web/shared/artwork/provider-images.ts:15` sets `dangerouslyAllowSVG:false`, remote sources are exact IGDB JPEG paths, and local optimizer sources are the controlled Open Library route. `next/dist/server/image-optimizer/transform.js:140-149` detects bytes before native optimization and throws400 for SVG independently of the HTTP Content-Type. The Next Sharp allowlist still enables SVG, so this is a supported-caller gate rather than removal of the SVG loader. TMDB's server cache passes through bounded, signature-checked raster bytes (`web/server/artwork/tmdb-poster-source.ts:13-36,48-63`); it does not call Sharp. Open Library accepts raster MIME types but lacks equivalent signature checking, so the optimizer's independent byte detector matters there.

Benign exact-image native probe: image `sha256:c04ceb1759155f4b84d00b0bf51f24e0280a174affb8197430f3934316952e1e` (Node24.22.3/libvips8.18.7). `native-image-probe.cjs` runs actual compiled registration, then exercises Next optimizer and direct Sharp on benign ASCII-compatible XML declarations. Optimizer rejects UTF8/CP949/ISO-2022-CN-EXT SVGs with400. Direct Sharp UTF8 SVG metadata succeeds; CP949 and ISO-2022-CN-EXT both fail with **Unsupported encoding**. The LD_PRELOAD interposer recorded **no iconv_open calls** in these cases or four generated JPEG/PNG/WebP/GIF optimization cases. Exit0. This covers those fixtures, not every image metadata path. The interposer only observes externally resolved `iconv_open`, not hidden/internal conversion mechanisms.

Exact retained upstream packaging explains the observed native behavior: `packaging-posix.sh:157-158` builds libxml2 with `-Dminimum=true`; libxml2 `meson.build:105-106` makes `want_iconv` false unless the iconv feature is explicitly enabled. Its default feature is auto (`meson_options.txt:37-40`). ICU is disabled by default too. `packaging-posix.sh:273-274` explicitly configures libarchive `--without-iconv --without-xml2`. Current native rebuild instruction patches do not change these flags. Thus generic libxml2 `encoding.c:1381` has an iconv-backed input route in source, and librsvg passes XML_CHAR_ENCODING_NONE (`xml2_load.rs:491-499`), but those facts alone do **not** establish that iconv-backed encoding handler is compiled into this configured native payload. The actual unsupported-encoding result is consistent with the minimum build.

GLib remains a real general charset caller: `glib/gconvert.c:67` opens the caller-selected conversion, `gio/gcharsetconverter.c:464` uses supplied `to/from`, and locale/filename helpers also convert. GLib was not built with all conversion capability removed. No supported application caller supplies CP949→UTF8//IGNORE, ISO-2022-CN-EXT source, or IBM1390/1399 output encoding to these APIs. The XML decoding path above is independently constrained. The static native call-site inventory includes available source paths; it is not a declaration that all conditional source branches were compiled.

### API and HTTP path

`src/RateFreak.Infrastructure/Artwork/ArtworkDecoder.cs:23-29` uses SKCodec, validates a static JPEG/PNG/WebP format and then decodes pixels; encoding output is WebP. The static format check occurs after SKCodec.Create, so it must not be claimed that unsupported bytes never enter native format sniffing. Existing binary probe lists no iconv imports in the shipped Skia payloads or .NET runtime/PAL binaries. This supports excluding a direct Skia iconv route; it is not proof that libc cannot be called indirectly. Existing API iconv consumers include libstdc++, libpsl/libunistring and apt. No supported image-decoder path invokes apt or exposes a caller-selected legacy text conversion.

The browser proxy uses Node fetch/byte streams and the provider clients use .NET HttpClient/JSON parsing rather than the bundled GLib/libxml2 interfaces. No application call exposes iconv's source/destination names. This is caller evidence, not a claim that every HTTP body or database is always UTF8. System libraries, operator-changed locales/environment and generalized URL/libpsl interfaces remain broader native capabilities outside these narrowed supported calls.

### Database maintenance path

`deploy/self-host/maintenance.py:104-106,167` invokes pg_dump/pg_restore with fixed arguments; Python tarfile handles artwork/key archives, and replay uses fixed SQL and Python/managed JSON text paths. It does not call libarchive or a generic XML decoder. Existing tools binary probe found no direct iconv imports in its PostgreSQL17 client executables/libpq or Python executable/extensions; only libstdc++/apt plus libc exports appear in its scanned inventory. This does not constrain all locale conversions inside dependent C++/libc libraries, modified environment variables, or unsupported manually invoked tools. Backup files remain bound to exact application image IDs and are operator-supplied protected artifacts, not arbitrary public archive uploads.

## Disposition and remaining limits

No affected conversion has been demonstrated reachable from the reviewed supported request/image/maintenance callers. There is positive gate and exact-image evidence for the most plausible SVG/libxml2 route, and no observed native iconv call in the tested raster cases. All affected gconv converters nevertheless remain available; broad library-level or arbitrary-locale clearance is not supported. These results can support **conditional caller-level non-reachability** under current source/configuration and supported operators, not a repaired-glibc claim or unconditional all-path exclusion.

If stronger defense in depth is required, explicitly block VipsForeignLoadSvg after Next initializes its allowlist (as done for HEIF); this matches the existing product SVG policy but would need focused tests and a new exact-image proof. A glibc package update fixing all three issues is stronger. Selectively removing gconv modules would affect multiple images and needs dedicated alias/cache/legitimate-conversion proof; it is not performed or recommended as an unverified quick change.
